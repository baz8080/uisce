## PR #10 — Track description changes via hash for re-inference
*merged 2026-07-06 · +106/−9*

### PR body

## Summary
- Add `description_hash`, `start_date`, `model`, and `prompt_version` to each inference record, plus a 15s read timeout on the local LLM call, so re-inference can be triggered by an actual description change rather than a naive "case_id already seen" check.
- Backfill the existing 5,911 JSONL records with those fields, verified against the exact release DB the original inference run used.
- Add `build_inferred_cases.py`, which collapses the append-only JSONL into a one-row-per-case `inferred_cases` table (`end_*`-prefixed columns, namespaced so future inference types can share the table without collisions), joinable against `cases` for SQL-side staleness checks.
- Replace the inference gate in `infer_duration.py` with a hash comparison: a case is only re-inferred if it's new or its current description hash differs from the last one inferred against.
- Ignore `.DS_Store`.

## Context
Uisce Éireann cases can flip Open→Closed or gain new description text between scrapes, and the old JSONL gate only checked whether a case_id had ever been processed — so cases that changed after their first inference were never revisited. This closes that gap using a hash of the description as the change signal.

The "Build DB" GitHub Action is currently disabled (`gh workflow disable`) while this pipeline is still being worked out — not part of this PR's diff, just noting the current repo state.

- [x] Verified the new incremental gate against real data (only the one known unprocessed case_id surfaces) and against a simulated description mutation on a scratch DB copy (correctly flags the mutated case for re-inference, leaves everything else alone)

## PR #11 — Compute outage duration in inferred_cases
*merged 2026-07-07 · +6011/−6*

### PR body

## Summary
- Add `end_duration_seconds` to `inferred_cases`, computed from `end_input_start_date` (UTC) and `end_local_date`/`end_local_time` (Ireland local time), converted via `zoneinfo` so DST transitions (IST/GMT) are handled correctly rather than with a naive fixed offset.
- Duration is `NULL` for `end_source` values where it isn't a measurable quantity (`not_found`, `lifted_immediate`), for the handful of cases missing a `start_date`, and for any case where the computed end precedes the start — the last of these traces back to already-known `start_date`/`end_date` unreliability in the source feed rather than a bug in this computation.
- When only an end date is known with no time of day, treat it as end-of-day (23:59:59) — this applies whenever `end_local_time` is missing regardless of `end_source`, since that turned out to happen for `completion_update` too, not just `scheduled_end_date_only`.
- `inferred_cases` is now dropped and recreated on each build rather than relying on `CREATE TABLE IF NOT EXISTS`, since it's fully derived from the JSONL and this avoids needing schema migrations as more fields get added.

## PR #12 — Pin inferred start date and fail clearly on stale DB
*merged 2026-07-08 · +61/−3*

### PR body

## Summary
- Pin `inferred_cases.end_input_start_date` to the earliest `start_date` ever recorded for a case_id across the JSONL's history, computed at build time in `build_inferred_cases.py`, rather than using whatever the latest inference record happened to capture.
- `build_inferred_cases.py` now checks upfront that every case_id referenced in the JSONL exists in the local `cases` table, raising an actionable error (naming the missing case_id range and how to fix it) instead of a raw `sqlite3.IntegrityError`.
- Add `notes/pipeline-dependencies.md` documenting the underlying coupling between the JSONL and `out/uisce.db` as independently-evolving artifacts, and why there's no automatic reconciliation between them.

## Context
Investigating duplicate case_ids in the JSONL (cases re-inferred after their description changed) surfaced two things:
1. `cases.start_date` can drift between scrapes for the same case_id — observed twice, both times with the exact same time-of-day but the date shifted forward by whole days, the same clamping artifact already documented for `cases.end_date` in `notes/data-quality.md`. The earliest-captured value is the more trustworthy one.
2. Building `inferred_cases` from a JSONL produced on a different machine (a faster laptop, used for a larger inference run) hit a foreign key violation — the local DB was stale relative to the case_ids the JSONL referenced. This is a real, expected coupling given the JSONL and DB evolve independently; the fix here is to fail with a clear, actionable message rather than build tooling to auto-reconcile them.

## Test plan

- [x] Verified the new preflight check against a deliberately stale DB copy: fails with a clear message naming the missing case_id range, instead of a bare `IntegrityError`
- [x] Verified a normal build (DB covering all JSONL case_ids) still succeeds

## PR #13 — Build inferred_cases table into the DB on the weekly CI build
*merged 2026-07-09 · +3/−0*

### PR body

## Summary
- Add a "Build inferred cases table" step to `.github/workflows/build.yml` that runs `build_inferred_cases.py` after `main.py` and before the DB is published, so every weekly release DB includes the `inferred_cases` table.
- The DB is downloaded-then-reused each run and `main.py` only ever `INSERT OR REPLACE`s cases (never deletes), so it's monotonically growing — meaning the case_ids referenced in the manually-committed `data/inferred_duration.jsonl` will always be a subset of whatever DB CI builds. This avoids the failure mode described in `notes/pipeline-dependencies.md`.
- No new dependencies or secrets needed — `build_inferred_cases.py` is stdlib + sqlite3 only.

## Test plan

- [x] Validated YAML structure/parses correctly and matches existing step style.
- [ ] Confirm the scheduled build run on GitHub Actions completes successfully and the published release DB contains the `inferred_cases` table.
