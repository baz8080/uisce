## PR #21 — Fix mobile stats layout; record and recover case close times (schema v2)
*merged 2026-07-21 · +580/−43*

### PR body

Two related threads: the site was showing figures that didn't belong to the month being viewed, and the underlying reason was that the DB had no way to express a past month at all.

## Site layout

The county row grid is `150px 1fr 200px`, needing ~378px before the bar gets any width. On a 375px viewport the whole stats column sat outside the card and `overflow: hidden` clipped it — the stray digits still visible were the counts column bleeding into view, and the availability percentage was gone entirely. A 640px breakpoint drops the bar onto its own line so name and stats share the first. No shortened labels needed; the full `135 disruptions / 49 open now` fits once the bar moves.

Separately, open-case figures are now hidden on any month but the latest. They're a right-now snapshot of `status='Open'` with no month dimension, so on a historic month they read as a claim about that month. This covers the national tile, the row badge, and both blocks in the expanded detail — including the `No open cases right now.` fallback, which would otherwise have asserted something worse than the original bug.

Verified at 375px and desktop, on both a historic and the latest month.

## Schema v2: `cases.closed_at`

The feed publishes only a case's *current* status and the upsert overwrites `status` in place, so the Open → Closed transition was observable exactly once and we were discarding it. `closed_at` is now stamped in the upsert when the previous status was Open and the incoming one is not.

Three properties callers need:

- **Observation time, not event time** — resolution is the build cadence.
- **`NULL` is ambiguous** — still open, or closed before the column existed. Pair it with `status`.
- **It is a floor** — 12% of newly-appearing cases are created and closed inside one gap between builds and are never observed open.

`IS` / `IS NOT` rather than `=` / `!=` because some rows carry a NULL status, which `!= 'Open'` would silently evaluate to NULL. Ordering the reopen branch first means a stale stamp can't survive a reopen.

### Migration

The published DB is downloaded and updated in place each build, and `CREATE TABLE IF NOT EXISTS` won't add a column to it. Rebuilding instead isn't free — the DB accumulates cases the feed no longer serves plus ~8k geocode cache entries — so this introduces a deliberately narrow ladder.

`MIGRATIONS` is `{version: {column: decl}}`, a shape that can only express additive nullable columns. Applied to a copy of the live 20MB DB: **0.7ms, no rows touched, `integrity_check ok`**. A DB missing any v1 column is still rejected rather than migrated.

The per-column guard is load-bearing: `create_db` declares every column and *then* calls `check_schema_version` with `user_version` still 0, so a per-version guard would fire a duplicate-column error on every fresh DB. There's a test pinning that.

## Recovering pre-v2 history

Two routes were checked before accepting that pre-v2 closures were lost.

**ArcGIS.** The layer declares `LASTUPDATE` and `CREATEDATE`, and `editFieldsInfo` names `EditDate`/`CreationDate`. Probed against the live service: both are NULL for all 8,155 records (`ENDDATE` returns 6,497 on the same query, so the query is sound), the editFields aren't exposed on this DeptView, `capabilities` is `Query` alone, and there's no archiving — so no change tracking and no `historicMoment`. The feed is a complete archive of *cases* but a pure snapshot of *status*. Written up in `notes/data-quality.md`, since those fields will keep looking promising.

**Release snapshots.** `out/cases.json` is overwritten and gitignored, but each build publishes a full `uisce.db` as a dated release — a snapshot series. Diffing consecutive `status` columns recovers the transitions.

| | |
|---|---|
| Closed cases | 7,613 |
| Recovered by replay | **1,816 (24%)** |
| Closed before 2026-06-30 | 5,797 — unrecoverable |

`uisce-replay-closed-at` recovers the same measurement the live path makes, so both share one column. It never overwrites an existing stamp (the live one is at least as precise), skips currently-open rows, and is idempotent — verified by re-running against the real DB, which stamped 0 more and left a live-path stamp untouched.

## Rolling this out

The migration needs no orchestration: `create_db` calls `check_schema_version` every run, so the next build migrates the release DB in place and publishes v2.

The replay is one dispatch. `Build DB` now takes a `replay_closed_at` boolean input, off by default, gating a step that runs **after** the pipeline — so the schema is already migrated and this build's own stamps are in (and won't be overwritten). The two then leave no gap: the replay covers snapshot-to-snapshot, the upsert covers the last snapshot to now.

1. Merge
2. Actions → Build DB → Run workflow, tick `replay_closed_at`
3. Expect `rows to stamp: ~1816 of ~7614 closed (24%)`

The step is left in place rather than removed afterwards — it's gated so it costs scheduled runs nothing, and it's the recovery path if the DB is ever restored from an older release.

## PR #22 — Build daily so closed_at resolution is a day, not three
*merged 2026-07-21 · +8/−5*

### PR body

Switches the `Build DB` cron from `23 17 * * MON,WED,FRI` to `23 17 * * *`.

## Why this is more than freshness

The gap between builds is the resolution of `cases.closed_at`, and a case that opens and closes inside a single gap is never observed open at all — so no transition exists to record. That was **12% of newly-appearing cases** under the three-a-week cron.

Daily shrinks that floor. It cannot remove it: every cadence has gaps, and the feed publishes no modification timestamp to close them with (`LASTUPDATE`/`CREATEDATE` are declared but 100% NULL — see `notes/data-quality.md`).

## The comparability catch

The 12% was measured under Mon/Wed/Fri, so **the undercount is not comparable across this change**. Months from August 2026 will carry a smaller one than July 2026, which means a month-on-month drop in closure counts could be an artifact of the old cadence rather than a real change. Recorded in `notes/data-quality.md` next to the original measurement, since that's where anyone reading the figure will look.

This matters for the eventual "closed in month M" site work: July should probably carry a caveat, or the series should start at August.

## Also updated

Three places quoted the old cadence and would have become wrong: `README.md`, the `uisce.replay_closed_at` module docstring, and the `data-quality.md` note. The replay docstring keeps both cadences with the changeover date, since it describes snapshots spanning it.

## Cost

~20MB per release, so daily is roughly 7GB/year of release assets against the previous ~3GB. Fine for a public repo, but worth knowing it grows — and it does improve future replay resolution, since each release is a snapshot.

142 tests pass, ruff clean. No code paths change.
