## PR #18 — Report notice-to-completion honestly, and pin the schema at v1
*merged 2026-07-20 · +363/−112*

### PR body

The published time metric claimed to be something the data cannot support. This fixes the naming, splits observation from plan, and pins the schema.

## Naming

What we measure is the span from **notice publication** to the end the notice reports — not outage duration. The feed never records when supply was lost. Renamed so the code says what it means:

| before | after |
|---|---|
| `end_duration_seconds` | `notice_to_end_seconds` |
| `median_fix_h` / `fixed_n` | `median_completion_h` / `completed_n` |
| `data/inferred_duration.jsonl` | `data/inferred_end_times.jsonl` |

The JSONL holds end-time *signals*; duration is computed later in `build.py`. Site copy now leads with the publication caveat and states plainly that every figure is a floor.

## Observed vs scheduled ends

The site pooled observed completions with scheduled ends under "median time to fix … resolved", claiming observation for both. Within the `outage` class that feeds the metric:

| end signal | n | median |
|---|---|---|
| `completion_update` (observed) | 3,166 | **17.0h** |
| `scheduled_end_with_time` (a plan) | 894 | **5.4h** |
| pooled — as previously published | 4,060 | 9.3h |

Scheduled ends were 22% of the metric and dragged the headline from 17.0h to 9.3h — a larger distortion than the start-side noise that motivated the pv3 discussion. They still **accrue** disruption time (a published plan is the best interval available) but are excluded from the median and reported separately as "+N scheduled-only". `OBSERVED_END_SOURCES` is the single switch.

## Schema pinned at v1

The `cases` schema is declared once in `create_db` and stamped into `PRAGMA user_version`; both `_ensure_*` `ALTER TABLE` helpers are gone. `check_schema_version` is the whole compatibility story — current passes, structurally-current-but-unstamped gets stamped in place, anything older is refused with rebuild instructions rather than migrated.

The stamp-in-place branch exists because the published DB reads v0 while already carrying every column, and it is an accumulating archive of a feed with no history — rejecting it would destroy data. Verified against the real DB: adopted and stamped cleanly. Package to 1.0.0.

## Site row layout

The longer counts string overflowed its column. Counts now stack to the left of the availability figure, with the numeral right-aligned and its label left-aligned in fixed sub-columns so both edges line up down the page; `tabular-nums` stops proportional digits shifting the auto-sized percentage column. Verified: every edge resolves to a single x across all 26 rows, no overflow.

Also: "n open now" plus a header on the expanded list make clear the open count is a right-now snapshot rather than a property of the selected month, and future-dated notices read "from" instead of "since".

## Two findings recorded but not acted on

- **Schedule overrun.** 90.3% of `completion_update` descriptions retain their originally-scheduled window, giving an overrun signal that **never touches `start_date`** — both timestamps come from the same text. A regex probe (zero inference spend) found 69.5% finish late, median +2.7h, only 8.8% within 15 min of their own estimate. Unvalidated; three known weaknesses documented.
- **Inference lag.** CI never runs `uisce-infer`, so 183 cases are un-inferred — **98% of them open**. They accrue to "now" because inference has not run, not because anything is ongoing. This inflates the newest month specifically. Options written up; deliberately not chosen here.

## Verification

114 tests pass, `ruff check` clean. New tests cover the observed/scheduled split and all four `check_schema_version` outcomes. Pipeline, inferred-build and site generation all run end-to-end against the real DB.

## PR #19 — Fix fresh-DB builds and stop accruing downtime for already-ended cases
*merged 2026-07-20 · +152/−23*

### PR body

Three related changes from a deep pass over the corpus and codebase:

## 1. `create_db` couldn't create a database

`CREATE TABLE cases` declared `work_category` twice (since the schema-v1 commit), which SQLite rejects. CI never hit it — it downloads the released DB first, so `IF NOT EXISTS` no-ops — and the test fixture hand-built the schema rather than calling `create_db`, so a from-scratch `uisce-pipeline` run per the README crashed after the geocoding step. Fixed, `create_db` takes a `db_path` like the other helpers, and a new test exercises the real declaration against a fresh path.

## 2. Cases whose own text says they ended no longer accrue downtime

The nulled negative-span family (extracted end precedes publication) is **532 cases**, not the ~19 the notes recorded. 28 of them were `Open`, and 12 outage-class ones were accruing population-weighted downtime toward the 14-day cap for works their own description says finished — in July alone, Kildare carried ~101k and Donegal ~66k fabricated person-hours. `ended_by_publication()` routes them (and `lifted_immediate`) to the token 1-second footprint; genuinely no-signal open cases accrue exactly as before (pinned by tests, and verified against the real DB at a fixed timestamp — only the four affected counties move).

`uisce-build-inferred` also now prints the real never-inferred backlog, computed after the rebuild so a stale local table can't fake it.

## 3. Notes brought up to date

- The 532 finding in full: distribution, the JSONL evidence that the feed re-stamps `start_date` in place (date part moves, machine time-of-day survives), the clean positive side, and both intuitive rescue routes measured and closed.
- The `HM`-format internal refs that make reference pairing structurally impossible for investigation notices (coordinate pairing works; value still ~0).
- The 498 scheduled→completion JSONL transitions as a stale-window-free validation set for the parked overrun probe.
- The phantom-backlog trap (stale `inferred_cases` table ≠ un-inferred corpus).
- Staleness fixes: CI cadence (3×/week), pv1-era JSONL figures, the completed pv2 corpus run, a renamed constant.

118 tests pass, ruff clean.

## PR #20 — Deploy the status site to GitHub Pages after the DB build
*merged 2026-07-20 · +21/−0*

### PR body

## Summary

Wires GitHub Pages publishing into the `Build DB` workflow so the static status site (`uv run uisce-site`) is regenerated and deployed after each DB build.

- Adds `pages: write` and `id-token: write` permissions (keeping `contents: write` for releases).
- After `Publish DB`, runs `uv run uisce-site` and uploads `out/site` via `actions/upload-pages-artifact@v3`.
- Adds a separate `deploy` job (`needs: build`) that publishes the artifact with `actions/deploy-pages@v4` in the `github-pages` environment.

The site build only needs `out/uisce.db` (produced earlier in the job) and the tracked `data/sa_pop.csv`, so no extra inputs are required. Site steps run only after a successful pipeline + release, so the published site always reflects a completed build.

## Manual step required

In **Settings → Pages → Build and deployment → Source**, set the source to **GitHub Actions**. The `deploy-pages` step fails until this is done.
