## PR #50 — End-time extraction: rules first, LLM fallback
*merged 2026-08-21 · +2014/−67*

### PR body

## What

`uisce-infer` now answers the templated majority of notices with CPU rules (`src/uisce/rules.py`, `rules-v1`) and falls back to the local LLM only for what the rules abstain on. The corpus turned out to be ~93% rigid template; the rules pass covers it in 0.6s where a corpus inference run takes ~11 GPU-hours.

## Evidence (full numbers in `notes/rules-vs-llm-end-times.md`)

- **Labelled rounds (354 rows across three rounds):** 0 wrong emissions everywhere; 110/110, 73/73 and 110/110 correct on answered rows.
- **Corpus shadow eval (10,860 hash-stable cases):** 92.7% coverage, 10,067/10,068 agreement on answered. The single disagreement is the LLM's error (case 237463: header `2:42pm`, model wrote `14:22`).
- **Fresh unseen draw (120 cases, 2026-08-21), human-labelled:** LLM 120/120; rules-v1 **110/110 on answered rows (0 wrong emissions) at 91.7% coverage**. None of these cases was used to derive or tune any pattern, closing the overfitting caveat.
- **First live hybrid run:** 4-case backlog → 1 by rules, 3 by gemma, correct stamps, `uisce-build-inferred` clean.

## Design

- Rules may only emit `completion_update` / `scheduled_end_with_time`; recurring windows, lifts, Irish, day lists, date-only ends and any ambiguity abstain to the LLM. `not_found` and `scheduled_end_date_only` are never emitted.
- Records stamp `model: "rules-v1"`; staleness keys on the model too, so bumping `RULES_VERSION` re-runs only rules-produced cases while a `PROMPT_VERSION` bump still re-runs everything. No JSONL schema change, no backfill of historical LLM records.
- New `uisce-eval-rules-shadow` command re-measures the corpus agreement; `uisce-eval-replay` grew `--extractor {llm,rules}`.
- `RECURRENCE_TEXT` moved from site.py to config.py so inference-side code shares it without inverting the pipeline direction.

## PR #51 — Deploy the site on push, independently of the data build
*merged 2026-08-21 · +111/−28*

### PR body

Stacked on #50 (retarget to `main` once that merges). Second of the pair follows: CI running the rules half of `uisce-infer`.

## Why

The site was only deployed by the `Build DB` workflow, so a UI change waited for the next scheduled data build — up to ~6h. The site is a pure projection of the published release DB, so it can rebuild on its own, the way esb and lifts already do.

## What

- New `.github/workflows/pages.yml`: downloads the latest release DB and runs `uisce-site` on `push` to `main`, `workflow_dispatch`, and `workflow_run` after a successful `Build DB` (a `GITHUB_TOKEN` push fires no `push` event, so the data build has to hand over explicitly). `concurrency: pages`, queued not cancelled.
- `Build DB` drops its site/deploy steps and the pages permissions — data-only now.
- The banner's "Updated N ago" now reads `data_as_of_iso` (`site.py:data_horizon` = `MAX(cases.last_seen)`, the last feed read) rather than the build clock — otherwise a UI-only deploy would reset it and hide the 24h "last build may have failed" warning. `generated` stays on the build clock for the footer. Payload-shape guard updated (one new top-level key), three tests added.
- README + a dated section in `notes/pipeline-dependencies.md`.

## Verified

`uv run pytest` (439 passed), `uv run ruff check`; local `uisce-site` against the current DB shows banner "Updated 12 hours ago" (data) with footer "Generated 2026-08-21 08:40 UTC" (build).

## PR #52 — Run the rules half of uisce-infer in CI and commit the JSONL
*merged 2026-08-21 · +74/−8*

### PR body

Stacked on #51 (which stacks on #50); retarget as each merges.

## Why

`uisce-infer` never ran in CI because the LLM fallback needs a local model, so every data build landed cases with no end signal until the next manual run — and that backlog is almost entirely *open* cases accruing to "now" (`notes/pipeline-dependencies.md`). After #50 the rules answer the templated ~93% in 0.6s on a CPU, so that half can run in every build.

## What

- `uisce-infer --rules-only`: answers what the rules cover, counts the abstentions (`N left for the LLM`), never opens a session. Default behaviour unchanged. Test added next to `test_rules_covered_run_never_touches_the_llm`.
- `Build DB` runs it before `uisce-build-inferred`, and after the release is published commits `data/inferred_end_times.jsonl` to `main` as `uisce-ci` (after publish so the JSONL never references a case the latest release lacks; `git pull --rebase` first).
- `.gitattributes`: `data/inferred_end_times.jsonl merge=union` — two appending writers (CI rules, local LLM residue); `build.py:latest_per_case` keys on `inferred_at`, so order is irrelevant.
- Docs: README's local-inference steps (pull first; the local run is the residue only), how-it-works Flow 2, pipeline-dependencies "mirror image" update, a dated section in `rules-vs-llm-end-times.md` recording why the JSONL stays here rather than a `uisce-data` repo or a release asset, and a CLAUDE.md settled row.

## Verified

`uv run pytest` (440 passed), `uv run ruff check`. Locally: `uisce-infer --rules-only` on the current DB (0 to do, 0.14s); `--force --limit 20 --rules-only` wrote nothing and reported 20 left for the LLM (the forced order starts at the 2022 boil notices; coverage over the full corpus re-measured at 93%). Two-writer simulation in a scratch repo: two EOF appends merge without conflict under `merge=union`.

After merge: `gh workflow run "Build DB"` should leave a `uisce-ci` commit on `main` and trigger `Build site` via `workflow_run`.
