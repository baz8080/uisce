## PR #32 — Per-area incident history, and a directory to reach it
*merged 2026-08-05 · +975/−37*

### PR body

The site could say how a county was doing this month but not what had ever happened where someone lives. Every county already broke down into named Census areas with per-month counts; this makes each of those a page listing the individual notices behind the numbers, and adds a directory of all 1,836 areas that links into them.

## What "a location" is

Three candidates, and the one already built wins outright. `cases.location` is 99.9% populated but has 4,028 distinct normalised values with 66% singletons — the drill-down already declined to key on it. The geocode cache's place names cover 46% of cases. The **census-derived area** is neither: `full_lat`/`full_lon` are 100% populated, `SmallAreaIndex.affected` and `TownLookup.dominant` already home every pin, and `build_site` already computes `area_of`. So no new geography, and coverage is effectively complete — 128 of 7,525 events land in `UNPLACED`.

## The payload, which is the whole design constraint

All 7,525 events serialised is 1.8 MB, more than twice `data.js`. So it is not in the payload:

| | raw | gzip | |
|---|---|---|---|
| `data.js` | 691,493 | 90,162 | **unchanged** |
| `index.html` | 52,413 | 16,911 | +11 KB raw for the view, route and links |
| `areas.html` | 292,975 | 32,707 | new, loaded only if visited |
| `h/*.js` | 1,846,326 | 200,924 | new, one county fetched on demand |

`write_site` owns the split and pops the history before `data.js` is serialised, so a field added to it cannot leak into the payload by omission — with a key-set snapshot test that fails loudly on the next well-meaning addition. Median county shard is 5 KB gzipped, Dublin worst at 23 KB, one request per county per session.

An injected `<script>` rather than `fetch`, for the same reason `data.js` is a `<script>`: the site has to work opened straight off disk. The cache-busting query is skipped on `file://`, where it would be part of the path and 404.

## Two records deliberately say less than they could

**An event that closed without ever reporting an end publishes no duration at all.** Those carry `resolve_case`'s token one-second footprint, so a number would print `0.0h` for **801 events** — a measurement nobody made, and the exact failure `ended_by_publication` and `boil_notice_fate` exist to prevent. Reusing `endBadge` verbatim would also have told all 801 they were "capped at 14 days", which is false: the cap applies only to the 64 *open* no-signal events.

**A recurring event publishes covered hours with the window series' span beside it, never the span alone** — 63h of works across seven nights inside a 153h series, not 153h of outage.

## The bug this uncovered

The county breakdown homes each *pin*; the history named each *event* once over its whole footprint. So a burst published across two settlements counted on both county rows but appeared in only one history — and **220 of the 1,830 areas in the county tables had no history at all**, their pages saying no notice had ever been published directly under a row that had just counted one. A directory makes that unmissable, since 12% of its links would land there.

Listing each event under every area its pins were homed to closes it completely:

| | before | after |
|---|---|---|
| county-table areas with a history | 1,610 / 1,830 | **1,830 / 1,830** |
| shards, raw | 1,555,611 | 1,819,550 |
| shards, **gzip** | 183 KB | **189 KB** |

764 events are multi-area; the duplicated records compress to almost nothing, so the honest version costs 6 KB gzipped across the whole site. `area_of` is untouched — an event still gets exactly one *name*, for the open list and the top ten; what changed is where it is *listed*. Records carry `areas` so a reader meeting the same burst twice is told why rather than concluding the site double-counts, and `people` stays the whole event's footprint on every listing, so the two pages and the top ten cannot disagree about how many people a burst reached.

The guard was checked against the old behaviour rather than assumed:

```
OLD (one area per event)   county tables ['T1','T2']  history ['T1']       -> FAILS
NEW (every pin's area)     county tables ['T1','T2']  history ['T1','T2']  -> PASSES
```

## What moved in the published figures

`event_meta` now covers every severity rather than outages alone, since an event is a `reference_num` and not a severity slice. A recursive diff of the whole payload against a fixed-clock baseline says the entire effect is **three fields on one row**: June's `MEA00113409` goes 3→4 pins, 3→4 confirmed, and starts 5 June instead of 6 June, because one of its four pins was classified non-outage and had been excluded from its own event's counts. **No median moved**, national or county.

## Noticed while building, and acted on

**15 events (0.2%) were seen to close before their announced start** — a notice for works on 8 August that stopped being listed on 31 July. "Closed" implies works that finished; those render as *withdrawn*.

**The recurring span is anchored at the first window opening, not at publication.** 153h, not the 165h notice-to-end — the 12 hours before the first window opened are not part of what the window spanned.

## The directory

1,836 areas, 26 county sections, a bounded sticky jump nav, notice count and population per row. **Not paginated**: the whole list is one document so Ctrl+F finds anything, and paging would break the search that makes a list this long usable. Standalone rather than a fourth view, so first paint does not carry a list most readers will never open. Areas with no notice at all — roughly 1,900 of the country's named areas — are left out; a page of them would say nothing.

`areas.html` is a template with an `<!--AREAS-->` marker rather than a verbatim copy, so its markup and CSS stay in an HTML file and only the rows come from Python.

## Verification

318 tests pass, ruff clean. Driven in the browser: one shard request per county with no second fetch for a second area, back/forward through overview → county → area, dark mode, mobile at 375px with no horizontal scroll, and jump-nav headings clearing the nav at three scroll depths.

Area codes are hostile to URLs — 31 contain a slash, 2,808 a colon, 15 an apostrophe, 4 are non-ASCII — so both segments are encoded on both entry paths. `ed:Cork:Whiddy/Bantry Rural`, `ed:Clare:O'Briensbridge` and `02341-Dún Laoghaire` were each round-tripped from the directory and as cold deep links.

## Not verified

**The `file://` path.** The in-app browser will not leave `http:` and the Chrome extension was not connected, so I confirmed the loader builds the right URL for both protocols (`file:` correctly omits the query; `h/kildare.js` resolves to the right sibling) but not that a browser actually loads the sub-directory script off disk. If it does not, the page shows its error copy rather than a blank card. Worth one manual open before this deploys.

## PR #34 — Rewrite the site for a general reader
*merged 2026-08-06 · +425/−80*

### PR body

The data work assumes a reader who wants to be told what a figure cannot say. The site had inherited that voice wholesale, and the site is for people who want to know whether their town's water has been alright.

Nothing here softens a claim. Every caveat is still on the page — layered, not deleted.

## Three figures were wrong, not merely dense

**`clear_days` counted days that hadn't happened.** Future days carry an empty severity, so `sum(1 for d in days if d[0] == "")` counted them as clear. Cavan read **27/31 clear days** on 6 August, with four bad days out of the six that existed. It was the only figure on the site that overstated rather than understated. Now emits `days_elapsed` alongside, using the same UTC-date predicate `dayCells` already applies client-side, and reads **3/6 clear days so far**.

**No pluralisation on the county view** — "1 supply disruptions", "1 planned works".

**`100.00%` beside a real disruption.** Two decimals guarantee it whenever a small event hits a large county; Cavan showed `100.00%` next to `1 supply disruption (114 person-hours)`. The *display* now clamps to 99.99% whenever person-time was actually lost. A genuine zero still shows 100.00%.

Four new tests cover the clear-days semantics, including an invariant that `clear_days` can never exceed `days_elapsed`.

## Structure

Counties move above the national tiles. The banner already carried the headline and the tiles duplicated two thirds of it, so nothing was lost above the fold — and on a 375px phone the first county row went from roughly 1600px down to the first screen. On narrow screens the colour legend also drops below the bars it describes, since it is reference material; the drinking-water key stays above, because that one is a warning rather than a key.

The 2,600-character methodology paragraph — nine distinct topics, 12.5px, muted grey — becomes seven named sections behind a `<details>`, with the A–F thresholds finally rendered as a visual key rather than buried mid-sentence. The dated methodology change gets its own disclosure, so it has somewhere to live next time.

## Vocabulary

`case`, `pin`, `event` and `the feed` are the database's nouns and the ArcGIS source's. The page now says **notice** and **incident** throughout. `floor` → `minimum`, `person-time` → `people's time`, `Pinned outside the county` → `Couldn't be placed in a town`.

## Content that only existed on hover

The health mark, the day bar, the availability meter and five column headers carried their meaning solely in `title` attributes. On a phone that is no explanation at all — and the health mark is the one thing on the site that bears on whether water is safe to drink.

The county view now shows a visible pill (*"3 drinking-water notices in effect"*), the day bar has a tap-to-read caption, and the two most-misread headers carry visible sub-labels (*people × hours*, *vs this area's own population*).

## The area directory

1,836 areas behind a county jump nav, with the page's own copy saying "pick one" — and no way to find your town unless you already knew its county, which is exactly what a reader is least sure of for the rural *Around …* areas. Adds a client-side filter over the rendered list: no new data, no request, and a county name matches its whole section.

Each row now names its own units (`Cootehill · 6 notices · 1,856 people`) instead of leaving two bare right-aligned integers under a heading that scrolls away after the first county — where most readers take the larger number for the notice count.

## Freshness

`data to 2026-08-05 22:07 UTC` asked every visitor to do timezone arithmetic to answer *is this current?*, and a dead build looked identical to a fresh one. Now relative, holding one unit to 24h and then saying the build may have failed, in `--critical`.

The reasoning is worth recording: the problem was never that 17 is a large number, it is that **a large number from a healthy schedule is indistinguishable from a build that died**. A friendlier word does not separate those; an explicit overdue signal does, and its absence then does the reassuring at no cost in words on a normal render.

A first pass switched to calendar-day wording above 12h. Simulated against the real cron, `earlier today` proved **unreachable** — by the time the 11:20 build is 12h old the 17:23 build has replaced it — and the branch that actually fired was `yesterday`, for a quarter of the day, in the morning reading window. Replaced with a single monotonic ladder, which is also what moment, Luxon and timeago all do.

`site.py` gains `generated_iso` (the existing human-readable field is not reliably parseable by any JS engine). The footer keeps the exact UTC stamp.

## Accessibility

County rows were `<div onclick=…>` with no role, tabindex or href — no county was reachable by keyboard or announced as interactive. They now wrap the name in a real anchor, the pattern the area rows already use, so middle-click and open-in-new-tab work too.

Also adds `meta description` and Open Graph tags: a public-interest site people link to had a blank preview.

## Verification

322 tests pass, ruff clean. Walked all four views plus `areas.html` at desktop and 375px, in light and dark; search checked across match / county-match / no-match / cleared; the freshness bands fed synthetic stamps at every boundary including month rollover and the 23:50-build-read-after-midnight case.

Two bugs surfaced only under that live check and are fixed here: `li { display: flex }` beats the UA stylesheet's `[hidden]` rule, so the directory filter set `hidden` on every row and hid nothing; and gating the overdue warning on *rounded* hours fired it at 23h30m against a threshold documented as 24h.

Left alone deliberately: the candour, `announced` as the load-bearing word, the five-way completion badge, and the paragraph explaining why there are no letter grades at area level.

## PR #36 — Keep hidden views hidden below 640px
*merged 2026-08-06 · +167/−0*

### PR body

Fixes the mobile regression from #34: on a phone, tapping a county appeared to do nothing, and reloading showed an empty box at the top with the county page mixed in below it.

## The cause

The four views (`#overview`, `#countyview`, `#areaview`, `#topview`) are switched by toggling the `hidden` attribute. The UA stylesheet implements `hidden` as a plain `display: none`, which **any** author `display` outranks — and #34 added `#overview { display: flex }` under 640px to reorder the front page on phones.

So below 640px the overview never went away. Tapping a county set `hidden = true`, rendered the county view *below* a still-visible overview, then scrolled to the top — of the overview. Measured at 375px before the fix:

```
overviewHidden: true, overviewDisplay: "flex", height: 3846, countyViewTop: 3988
```

On reload at `#county/…`, `renderOverview()` never runs, so the top of the page was an un-rendered overview — the "empty box" is the unfilled `.banner`, which has its own border and padding — with the county view thousands of pixels below.

Not device-specific: it reproduces in any browser at a narrow window, which is why Safari and DuckDuckGo behaved the same.

## The fix

One rule, guarding the attribute rather than the one id:

```css
[hidden] { display: none !important; }
```

`#overview[hidden]` would also work, but only for that id. The `!important` keeps `hidden` meaning hidden whatever display a future view needs. `areas.html` already carries the id-specific version of this (`li[hidden]`) with a comment describing the same trap.

## Tests

There's no JS or browser test infrastructure here, so `tests/test_site_css.py` runs a small CSS cascade in Python: it parses the `<style>` block and, for each element either page hides, works out which `display` actually wins with `hidden` set, in every media context the stylesheet defines. It reads the view ids out of the router's own `VIEW_EL` map, so a view added later is covered without touching the test, and it also checks `areas.html`'s search-filtered rows.

Verified to fail on the pre-fix file with the precise diagnosis:

> `site.html: {'tag': 'div', 'id': 'overview'} is display:flex while [hidden] is set under @media (max-width: 640px)`

A second test pins that the fix wasn't to delete the flex ordering: `#overview` must still get `display: flex` in that media query while resolving to `none` when hidden.

## Verification in a browser

At 375px, county → area → `#top` → back each show exactly one view, the drill-down landing at y=142 with no horizontal overflow (`scrollWidth == innerWidth == 375`). At 1280px the overview returns to `display: block` and the desktop layout is unchanged. Full suite: 325 passed, ruff clean.
